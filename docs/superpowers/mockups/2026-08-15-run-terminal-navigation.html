Where terminals live

Today every mode parks its list in the Companion: Talk keeps its chats there, Direct its runs, Run its terminals. That worked while the Companion was the only shelf in the app. Now that the mode band carries its own line and the Companion runs floor-to-ceiling, the Run list is the one that fits worst — a terminal is not a document you pick from an index, it is the room you are standing in. Three ways to move that navigation next to the work, all three live below.

Shipped: the session rail (A) + the ⌘⌥K switcher (C), with the icon layer Audited: CompanionTerminals · terminalsStore · TerminalPane · App.tsx Run panel · ModeBand Palette and icons: real tokens from src/styles.css, real lucide geometry

The read

What the current arrangement actually costs

The mechanics are sound — terminalsStore already models everything a good switcher needs, and PTYs survive every unmount. The problem is placement and what the panel chooses not to show.

01

Collapsing the Companion deletes terminal navigation.The panel is the only pointing device for switching sessions. Collapse it — a gesture the app invites, with more canvas as the reward — and only ⌘⌥1..9 remains, undiscoverably.

02

The switcher sits at the far edge of the screen from the terminal.You read output at the left of the canvas and steer sessions 900px to the right. Every switch is a full-width eye and mouse trip.

03

A 262px column holds four words.Terminal names are short — main, dev, tests. A full sidebar column spends premium horizontal space on a list that would fit in a strip.

04

The state we already track is invisible.TerminalState.busy — the daemon's real foreground signal — is computed, stored, and used by the workspace rail, but the Terminals panel never renders it. A running npm run dev and an idle shell look identical.

05

A bell tells you the workspace, not the terminal.attentionStore flags per workspace, so with three sessions open you learn that something rang and get to find out which.

06

Run's Companion has one job and does it thinly.Talk's Companion carries history, context, savings and the logbook. Run's carries a four-row list — the panel is mostly empty, and the list itself is the least suitable thing to fill it with.

The prototype

Three arrangements, live

Chosen: the rail plus the switcher — the first tab is the shipping design; B and C stay for comparison. Everything inside the frame works: click a session, add one, close one, press ⌥1…9 to jump, ⌥K for the switcher, and hold ⌥ or ⌘ to watch the rail flip from icons to jump numbers. The second control switches the mode band between words, icons + words, and icons alone. Use the simulation buttons to fire a bell or start a build in a session you are not watching — that is the moment each design is really being judged on.

The options

What each one is, and what it costs

Option A
The session rail
44px, canvas-left, always there.

A slim column flush to the left of the terminal, built from the grammar the app already uses twice — the workspace rail and the hunk rail. Each session is a numbered cell, and the number is not decoration: it is the ⌘⌥N shortcut, so the rail teaches the keyboard path just by existing. State lives in the cell's own edge: brass when active, marching brass segments while a command runs, a single brass dot when it rang while you were elsewhere.

Names are one hover away in a flyout that carries the full label, working directory, uptime, the running command, and the rename and close actions the Companion holds today. Because the rail lives inside the canvas, it survives collapsing the Companion — which then becomes a proper session inspector rather than the only way to steer.

Buys
  • Navigation that never disappears, whatever the Companion is doing.
  • Costs 44px of width and zero height — the terminal keeps its rows.
  • Scales past nine sessions without truncating a single name.
  • Makes the numeric shortcut discoverable for the first time.
Costs
  • Labels are behind a hover — the weak spot when sessions are dev, dev-2, dev-3.
  • Two vertical rails on screen; the left edge gets busy at narrow widths.
Reuses: WorkspaceRail cell + identity-edge pattern · .rail-bar-running marching bar · .octo-menu-enter flyout · beacon law for the bell.
Touches: new SessionRail.tsx in the Run panel · CompanionTerminals becomes a detail panel · per-terminal attention in attentionStore.
Option B
The session ribbon
32px, above the terminal, names visible.

One mono line directly above the output, using the tab grammar Review already ships in EditorTabs — brass underline on the active chip, brass-faint fill, hover-revealed close, drag to reorder. Nothing new is invented; the pattern is simply extended to the surface where developers most expect to find it.

Each chip reads 1 · main with a state dot: verdigris idle, a marching brass underline while a command runs, a brass dot when it rang. Overflow scrolls with the chevron pair the Direct run track already uses. Double-click still renames inline, exactly as it does today, so no muscle memory is lost.

Buys
  • Names always legible — the only option with zero hidden identity.
  • Instantly familiar; no gesture to learn, no tooltip to discover.
  • Close and rename stay where the eye already is.
Costs
  • Takes 32px of terminal height, permanently, on every workspace.
  • Room runs out around six sessions; then it scrolls and identity hides anyway.
  • The most generic of the three — it is what every terminal app already looks like.
Reuses: EditorTabs chip geometry and drag-reorder · RunFlowNav overflow chevrons · existing inline-rename gesture.
Touches: new SessionRibbon.tsx above the Run canvas · same Companion and attention changes as A.
Option C
The anchor & switcher
Zero standing chrome; one chip and a palette.

The mode band's status tail stops being a read-out and becomes the control. Instead of "3 terminals" it reads 2/3 · dev · npm run dev with a live state dot — telling you which session you are in, how many exist, what it is doing, and whether another one wants you. Clicking it, or pressing ⌘⌥K, opens the switcher: the Command Palette pattern, scoped to sessions, with search, state, working directory, last command, arrow-key selection and delete-to-close.

The canvas is then 100% terminal, and the Companion collapses by default in Run mode. ⌘⌥←/→ cycles without opening anything. This is the most opinionated option: it treats terminal switching as an action you invoke, not a list you keep on screen.

Buys
  • The largest terminal in the app — no rail, no ribbon, no panel.
  • Scales to twenty sessions as gracefully as to two; search beats scanning.
  • Richest per-session information at the moment of choosing, not before it.
  • Keyboard-first, which is what a terminal user already is.
Costs
  • You cannot see your other sessions at a glance — only the anchor's summary.
  • Discoverability rests entirely on one small chip in the band.
  • Switching becomes two steps for the mouse user who never learns the shortcut.
Reuses: CommandPalette + ModalShell align="top" · the band's existing tail slot and FadeSwap.
Touches: ModeBand tail becomes a slot for a control · new SessionSwitcher.tsx · Run defaults the Companion collapsed.

The decision

The rail ships, and takes the switcher with it

The rail is the one arrangement that is both always-present and native to this app's grammar — it is the workspace rail's sibling, one level down, and it costs the terminal no rows. Its single weakness is hidden names, and C's switcher answers precisely that: ⌘⌥K gives you search, working directories and last commands whenever four numbered cells are not enough. Two surfaces, one for glancing and one for finding, both already in the design language.

B is the safe answer and would ship fastest, but it spends terminal height forever to solve a problem a hover already solves, and it makes Run mode look like every other terminal app — which the product's own positioning treats as a negative signal.

The anchor in the band comes along for one specific reason: a keyboard-only switcher is a switcher nobody finds. The tail already existed and already talked about terminals — turning it into ⌘⌥K · dev · npm run dev makes the palette discoverable by mouse and names the shortcut in passing, without adding a single new piece of chrome.

1Render TerminalState.busy everywhere a session appears — that signal is already in the store and is the single biggest legibility win.
2Give attentionStore a terminal id alongside the workspace id, so a bell points at one session instead of a whole workspace.
3Ship SessionRail.tsx in the Run canvas and SessionSwitcher.tsx behind ⌘⌥K and the band anchor; Run's Companion becomes the session inspector — role, path, pid, uptime, restore state, rename, close. No capability is lost, only relocated.
4Add the icon layer below: four mode icons, and one session icon derived from what is running.
5Keep ⌘⌥1..9, add ⌘⌥←/→, and update docs/FEATURES.md in the same change.

The icon layer

Two icon questions, and they are not the same question

"Run" is a word, and words carry culture: it reads as execute something to one developer and as where my shells are to another. That is a mode-level problem. Whether each session deserves its own icon is a different problem with a different answer — and the wrong answer to the second one is the most common icon mistake there is.

1 · The mode needs an icon because the word is ambiguous

Icons go on all four segments — icon-only on Run would read as a special case rather than a mode. The label stays: mode navigation is the one place in the app where a wrong guess costs the most, so this is not where we spend a tooltip. Toggle the band control above the frame to compare words, icons + words, and icons alone.

RunSquareTerminalA window with a prompt inside — the room, not the verb.
TalkMessageSquareConversation, unmistakable at 13px.
ReviewGitCompareTwo branches meeting — the diff, not a generic eye.
DirectWaypointsThe pipeline's own shape: nodes on a track.

Considered and rejected: renaming Run to "Terminal". It clarifies one segment at the cost of the set — Talk / Run / Review / Direct are four things you do, and one noun among three verbs reads as an accident. The icon buys the same clarity without breaking the grammar.

2 · The session icon must encode difference, or it is decoration

A terminal glyph on every cell says "this is a terminal" four times over — information the user already has. So the session icon answers the only question the label cannot: what is running in there right now. That is derivable, not invented — the daemon already samples each PTY's foreground process every tick.

Rule 1
The icon is the identity; the number is the address. A 32px cell holds one glyph well and two badly, so the rail shows the icon at rest and flips every cell to its ⌘⌥N number while ⌥ or ⌘ is held — the hint arrives exactly when the hand is already on the modifier. Nothing lives only behind that gesture: the number is permanently visible in the hover flyout, the Companion inspector and the switcher.
Rule 2
Roles are sticky. The icon follows the last significant foreground command, not the instantaneous one. A dev server that finishes a rebuild is still the dev server; a session whose identity flickered every time a command exited would be worse than no icon at all (stability doctrine S1 — slots hold their meaning while things run).
Rule 3
One glyph, two facts. The icon carries identity, its colour carries state: verdigris idle, brass while busy or ringing. No icon-plus-status-dot pairs anywhere — that is the double encoding the minimalism doctrine exists to prevent. Brass stays surgical: the active cell, and the one session holding the beacon.

What this asks of the backend

One bounded change. The PTY daemon already resolves each session's foreground process group every tick — Session::check_attention and check_foreground take the tcgetpgrp result and sample that pid's CPU — but the foreground event only carries { sessionId, busy }. Widen it to { sessionId, busy, command? } by reading the pid's name (/proc/<pid>/comm on Linux, proc_pidpath on macOS). Classification then lives in the frontend as a pure, unit-testable lib/sessionRole.ts with an honest fallback — no new IPC command, no new table, no polling.

Deliberately not in v1: user-assigned icons or emoji per session. The label already carries user intent, and a picker is a preference to maintain plus a decoration when nobody fills it in. If auto-classification proves ambiguous in daily use, the override belongs in the flyout — one line, added later, against real evidence.
